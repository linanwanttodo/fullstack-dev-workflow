# Trigger Eval

验证 SKILL.md 的 `description` 是否会正确触发（加载）这个 skill。description 是
skill 被调用的唯一入口——触发错了，后面全部白搭。这是三份评测里最容易被跳过、却最
影响实际使用的一份。

## 查询集（20 条，含近失例）

期望：开发类请求 → YES；非开发类 → NO。近失例（15-20）是刻意选的和开发沾边但本质
不是的请求。

| # | Query | Gold |
|---|---|---|
| 1 | 帮我修一下这个 bug | YES |
| 2 | 这个功能怎么实现？ | YES |
| 3 | 设计一下这个 API | YES |
| 4 | 这个项目架构怎么设计的 | YES |
| 5 | review 一下代码 | YES |
| 6 | 为什么这个接口这么慢 | YES |
| 7 | 帮我把这个模块重构一下 | YES |
| 8 | 数据库表怎么设计 | YES |
| 9 | 写个单元测试 | YES |
| 10 | 部署到生产环境怎么配 | YES |
| 11 | 这个代码安全吗 | YES |
| 12 | 帮我写提交信息 | YES |
| 13 | 快速把按钮颜色改成蓝色 | YES（快速 UI 修改也是开发） |
| 14 | 把那个常量从 20 改成 30 | YES（单行改动也是开发） |
| 15 | 帮我写一首诗 | NO |
| 16 | 2+2 等于几 | NO |
| 17 | 今天的天气怎么样 | NO |
| 18 | 帮我把这段话翻译成英文 | NO |
| 19 | 解释一下什么是量子力学 | NO |
| 20 | 帮我生成一张风景图 | NO |

## 运行方式

把**当前 description** 和这 20 条查询发给一个 fresh subagent，让它逐条判 YES/NO
（严格按描述逐字读），然后与 gold 对照算准确率。若对同一查询改了几版 description，
同场对比（见下方历史）。

## 评分

- 准确率 = 命中 gold 数 / 20。通过线 ≥ 0.95（应全对；近失例是防过拟合的护栏）。
- 两条 description 同分时，选对**未在测试集里**的边界情形更稳的那个（描述里显式的
  "Do NOT use for…" 负向条款比隐含边界稳健——见 2026-08-18 记录）。

## 历史回归

- 2026-08-18：DESC-A（原版）与 DESC-B（候选，含负向条款）同场对比，均为 20/20。
  因 DESC-B 对测试集外的边界情形（非开发请求却提到 "quality"/"requirements doc" 等
  开发词汇）更稳，采用 DESC-B 并写入 `SKILL.md`。未来改 description 后重跑本集，确保
  不低于 20/20 且不误伤 15-20 号近失例。
